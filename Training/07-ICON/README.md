# Installing ICON

Clone the latest stable branch/tag, as some external dependencies come as git submodules
fetch also them:
```
git clone --recurse-submodules -b release-2024.07-public https://gitlab.dkrz.de/icon/icon-model.git
```

ICON has some external dependencies, most importantly `eccodes` and `netcdf` libraries.
In Mahti those are readily available, but in some other systems one might need to install them first.

Copy the config scripts from SCC repo (`applications/icon/config`) to `config/csc` under `icon-model`. Next, create
a build directory, run the config script, and then build the code with `make` (`-j 8` 
means use 8 processes to speed up building):
```
cd icon-model
mkdir build-cpu
cd build-cpu
../config/csc/mahti.cpu.gcc-11.2.0
make -j8
```

For GPU version, name the build directory e.g. `build-gpu` and use `mahti.gpu.nvidia-22.3` config script

# Running ICON

ICON uses "runscripts", *i.e.* shell scripts which contain Slurm parameters together with
the actual climate model setup. Due to scripting mechanism runscripts need to be under 
`run` directory with the "build" directory, and submitted from therein.

The model setup is contained in files named with `exp.` prefix, for example, `exp.NextGEMS_R2B4`. The actual runscript can then be generated by `make_runscripts` shell script, which need to be run within the **"build"** directory. When executing `make_runscripts`, the `exp.` prefix is left out:
```
# e.g. within build-cpu
./make_runscripts NextGEMS_R2B4
```
Outcome is the runscript `exp.NextGEMS_R2B4.run` under the `run` directory. In the systems
known by the build system, runscript already contains usable Slurm etc. settings, however, in Mahti more manual editing is needed. (We will look later on how to add settings for
competition cluster into the build system).

## Common settings for CPU and GPU runs

After generating `exp.NextGEMS_R2B4.run` with `make_runscripts`, change into the `run`  directory and open the file with your favourite editor.

Duration of simulation is specified in `start_date` and `end_date` variables, and is in the example script four days. In order to reduce the running time in this exercies, let's simulate only 12 hours by changing end time into:
```
    end_date=${end_date:="1979-01-01T12:00:00Z"}
```

Large input files (horizontal grids, greenhouse gases, initial conditions etc.) are normally stored in central location given in `icon_data_rootFolder` variable. In unknown systems the default is under users HOME directory. We have already copied data required for the the NextGEMS_R2B4 experiment to Mahti, so set the variable as:
```
export icon_data_rootFolder="/scratch/project_2009905/pool/data/ICON"
```

## Settings for CPU run

Add relevant `#SBATCH` settings to the beginning of `exp.NextGEMS_R2B4.run` (right under `#! /bin/bash`). Let's try first with single node, 32 MPI tasks and 4 OpenMP threads, you may look CSC user documentation at https://docs.csc.fi/computing/running/example-job-scripts-mahti/ for further information. Modify also the existing `OMP_NUM_THREADS` and `ICON_THREADS` settings accordingly.

As we are using Slurm, set also the command to start the model as `srun`:
```
export START="srun"
```

You should be now ready to launch the model with `sbatch`. As we have special reservation for the training you may use the `-R` flag:
```
sbatch -R scc-cpu exp.NextGEMS_R2B4.run
```

The log output of the simulation will be in the stdout/stderr of the Slurm job (within the submission directory). In ICON runscripts it is typical to direct Slurm output into specific files, e.g.:
```
#SBATCH --job-name=exp.Nextgems
#SBATCH --output=LOG.%x.%j.o
#SBATCH --error=LOG.%x.%j.o
```
(`%x` will be replaced by job name, and ´%j` by job number).

Runscript copies relevant input files into `experiments/EXPNAME` under the "build" directory, also the large output files will be there. At this step it is, however, enough, to investigate the log output.

Tasks with CPU runs:
1. Try to determine simulated days per day (SDPD) based on the start and stop dates (can be found also in the log output) and the timing output in the end of the log output (use `total` timer).
2. Try different combinations of MPI tasks and OpenMP threads, e.g. 1, 2, 4, 8 OpenMP threads (and keep the product of OpenMP threads to MPI tasks per node as 128). Which setting give the best performance?
3. Try different values for `nproma` variable in the runscript, e.g. 24, 32, 48, 64 (use the same value for `nproma_sub`). Which setting gives the best performance?


## Settings for GPU run

Add relevant `#SBATCH` settings to the beginning of `exp.NextGEMS_R2B4.run` (right under `#! /bin/bash`). Let's try first with single node and single GPU, you may look CSC user documentation at https://docs.csc.fi/computing/running/example-job-scripts-mahti/ for further information. As we use later on multiple GPUs, use the `gpumedium` partition.

ICON itself does not set correct mapping between MPI tasks and GPUs within a node (i.e.
by default all the MPI tasks use only GPU 0). Thus, a special wrapper script is needed, which sets different value for `CUDA_VISIBLE_DEVICES` environment variable for different 
processes. SCC repo contains ready-to-use script `applications/icon/run_wrapper/mahti_gpu.sh`. In order to use the wrapper script, set the START variable as follows:
```
export START="srun full_path_to_wrapper"
```
The full path can be found by the `realpath` Linux command, e.g. by running in the topmost level of the repo
```
realpath applications/icon/run_wrapper/mahti_gpu.sh
```

You should be now ready to launch the model with `sbatch`. As we have special reservation for the training you may use the `-R` flag:
```
sbatch -R scc-gpu exp.NextGEMS_R2B4.run
```

The log output of the simulation will be in the stdout/stderr of the Slurm job (within the submission directory). In ICON runscripts it is typical to direct Slurm output into specific files, e.g.:
```
#SBATCH --job-name=exp.Nextgems
#SBATCH --output=LOG.%x.%j.o
#SBATCH --error=LOG.%x.%j.o
```
(`%x` will be replaced by job name, and ´%j` by job number).

Runscript copies relevant input files into `experiments/EXPNAME` under the "build" directory, also the large output files will be there. At this step it is, however, enough, to investigate the log output.

Tasks with GPU runs:
1. Try to determine simulated days per day (SDPD) based on the start and stop dates (can be found also in the log output) and the timing output in the end of the log output (use `total` timer).
2. The default `nproma` is very bad for GPUs, try to increase both `nproma` and `nproma_sub` to 6000. Does the performance improve?
3. Run by using all the four GPUs in the node, how much does the performance improve?
